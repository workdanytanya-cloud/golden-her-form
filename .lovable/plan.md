
## Что сейчас работает правильно

- **Регистрация** — есть, `/auth`.
- **Блокировка разделов до одобрения** — `AccessGate` уже закрывает тренировки/питание/прогресс на статусах `pending_onboarding` и `awaiting_approval`. Клиент видит понятную заглушку.
- **Смена статуса при отправке анкеты** — триггер `mark_client_awaiting_approval` переводит `client_access` из `pending_onboarding` в `awaiting_approval`.
- **Уведомление тренеру** — триггер `notify_admin_on_onboarding` создаёт запись в `admin_notifications` + realtime-колокольчик в админ-панели.
- **Активация доступа тренером** — на карточке клиента есть кнопка «Открыть доступ» → `client_access.status = 'active'`.
- **Генерация программ** — есть `generateProgram` (тренировки) и `generatePlan` (питание) из данных анкеты.

## Что нужно доработать

### 1. Обязательные поля в анкете
Сейчас проверяется только `goal_primary`. Нужно:
- Пометить каждое обязательное поле красной звёздочкой в UI.
- При «Отправить тренеру» — валидировать все обязательные поля; при отсутствии показать список незаполненных, подсветить их красной рамкой и проскроллить к первому.
- Черновик («Сохранить») по-прежнему сохраняется без валидации.

Обязательные (для качественной программы): основная цель, опыт, дней в неделю, длительность тренировки, локация, фокус-зоны, травмы (да/нет + детали если да), сон, уровень стресса, энергии, вода, тип питания, приёмов пищи/день, уровень активности, срок цели.

### 2. Автогенерация программ после отправки анкеты
Сейчас программы создаются тренером вручную. Добавить:
- Автоматическую генерацию **черновика** тренировочной программы и плана питания сразу после отправки анкеты (в тот же upsert-хендлер онбординга).
- Черновики уходят в `training_programs` / `nutrition_plans` со статусом «draft» — клиент их пока не видит (доступ всё ещё `awaiting_approval`).
- Тренер на карточке клиента видит уже готовые черновики, при желании правит и жмёт «Открыть доступ».

### 3. Очередь новых анкет у тренера
Сейчас в `/admin` — плоский список клиентов. Добавить:
- Секцию «Новые анкеты» вверху с клиентами в статусе `awaiting_approval`.
- В таблице клиентов — колонку «Статус» с бейджами: Анкета не заполнена / Ожидает / Активен / Приостановлен.
- Сортировка: сначала ожидающие, затем активные.

### 4. Уведомление клиенту об открытии доступа
Сейчас клиент не узнаёт, что доступ открыт. Добавить:
- Таблицу `client_notifications` (id, user_id, type, message, is_read, created_at) c RLS «свой user_id».
- Триггер: при переходе `client_access.status` в `active` создать уведомление «Тренер открыл вам программу — можно начинать».
- Иконку-колокольчик в шапке личного кабинета (аналог админской) с realtime-подпиской и toast-ом.
- На главной дашборда — заметный баннер «Доступ открыт» пока клиент не отметит прочтение.

## Технические детали

- Миграция: таблица `client_notifications` + GRANT + RLS (SELECT/UPDATE своих) + realtime publication + триггер на `client_access` (AFTER UPDATE OF status).
- Функция генерации: обёртка `autoGenerateDraftsForClient(userId)` в `src/lib/` — вызывается из `dashboard.onboarding.tsx` после успешного upsert с `completed_at`, и (для идемпотентности) из карточки клиента кнопкой «Пересобрать черновики».
- Валидация анкеты: массив `REQUIRED_FIELDS` + функция `validate(form)` → `string[]` (список ключей), рендер ошибок над формой + `data-field` + scrollIntoView первого пустого.
- Клиентский `NotificationsBell` — переиспользовать компонент админской версии, параметризовать по таблице/фильтру.
- Админ-index: один запрос с join на `client_access` + сортировка по приоритету статуса.

## Порядок реализации

1. Миграция `client_notifications` + триггер активации.
2. Валидация обязательных полей в `dashboard.onboarding.tsx`.
3. Автогенерация черновиков программ при отправке анкеты.
4. Клиентский колокольчик + баннер на дашборде.
5. Очередь новых анкет и бейджи статуса в `/admin`.
